## Actionable findings

1. **P1 — Expired promise windows can still produce a write with a past date.** `workflow_runtime.py:1120-1134` constructs a floor offer without checking `no_window`; `workflow_runtime.py:1064-1071` accepts it directly without `_apply_proposal` validation. The newly added guards at lines 629-631, 679 and 755 do not cover this path. Direct initialization with `past_deadline=no_promise`, `day_of_month=1`, offset 0, preceding adjustment, and today 2026-10-14 correctly sets `no_window=True` and deadline 2026-10-01. Then `too_much`, `accepts`, `confirms` produces `next=create_promise`, `w_amount=100.00`, `w_date=2026-10-01`. This both violates no-promise policy and asks the bank to record a past date. Guard every offer/acceptance path, including the initial floor offer; add a regression covering this path, not just pays-today followed by refusal. Evidence: `probes.json`, `expired_window`.

2. **P2 — Explicit “next Tuesday” can be silently changed to an offer two weeks away.** `workflow_runtime.py:123-124` returns the current offer whenever its weekday matches, before respecting the extracted relative qualifier. On Wednesday 2026-10-14, with offer Tuesday 2026-10-27 and `prop_relative=next`, v24 resolves 2026-10-27; v23 resolves 2026-10-20 under the fixture's following-week policy. A customer correction can become an acceptance of the wrong date. Restrict the offer-restatement heuristic to genuinely unspecified relative dates, or establish that the explicit qualifier resolves to the offer before using it. Evidence: `explicit_next_weekday` versus `v23_explicit_next_weekday`.

3. **P2 — An aside accompanying final confirmation is never answered.** `workflow_runtime.py:1403-1410` handles readback and closing routes but not `write_step`. A readback response extracted as `rb_intent=confirms, aside=robot` routes to `write_step` at line 1220 and places the robot response into `neg_instruction`, which is no longer spoken. After a successful promise, `st_finalize` produces the normal goodbye without the response. This is exactly a supported new aside-schema case (`compile.py:376`), and also affects scam questions accompanying confirmation. Preserve pending aside speech through the write/finalization path. Evidence: `confirmation_aside` includes both the unused instruction and final goodbye.

4. **P2 — Composite deadline validation accepts invalid children and skips attempt validation.** `policy.py:430-434` checks child kind names and then continues the band loop. A valid fixture with an `earliest` rule containing `day_of_month=40` and `nth_business_day=2` returns no validation errors, but `bankcal.deadline` returns null. At runtime initialization, line 628 raises “Cannot resolve policy deadline”, terminating the call via the technical-error path. Missing adjustments, invalid offsets/counts and invalid attempt values are likewise skipped. Validate every simple child with the same checks as a standalone deadline and run attempts validation for composite bands. Evidence: `invalid_composite`.

## Specific requested risk assessment

**Aside wording:** the fixed prefix itself produces grammatical independent sentences; no deterministic awkward-sentence defect was established. There is a functional lost-answer defect above. The negotiation instruction can literally become `First answer ... Then: ` with an empty continuation on the confirmation path, but that instruction is unused there. Naturalness of model-generated negotiation speech cannot be established by offline code inspection.

**Goodbye / idle closing:** an explicit goodbye at readback now abandons unsaved proposals and finalizes, which is consistent with an unambiguous request to end the call. The eight-turn negotiation idle threshold is already in v23 and is not a v24 regression. It includes scam questions in “idle”, so it can stop a conversation containing eight such classified turns; that is inherited behavior. A separate v24 change at `workflow_runtime.py:1205` makes the sixth readback `other` turn count as repeated refusal even without a goodbye: v23 asks what amount/date to change, whereas v24 marks the proposal refused and routes to finalize. The direct probe proves this behavior (`sixth_readback_idle` versus `v23_sixth_idle`). Whether six correctly classified nonanswers should end a call is a product-policy choice; the implementation should not be described as closing only on explicit goodbye. No language-classifier accuracy claim is made.

**Month boundaries / floor kinds:** direct calendar probes correctly clamp January 31 + one month to leap-day 2028-02-29, roll January 1 across the holiday/weekend to 2027-01-04, and roll calendar October month-end forward to 2026-11-02. No month arithmetic defect was demonstrated for these supported explicit semantics. The significant boundary-related defect is the expired-window floor path in finding 1. A day-of-month in the current month can legitimately be past; `no_promise` must apply to every route. Composite validation is also incomplete as described above. These samples are not an exhaustive proof of all calendars, floors, or external fixture semantics.
